## 1. 结论

- **骨架质量高于一般 demo**：`core/` 零 UI 依赖、前端互不 import 的边界纪律在代码里成立；默认拒绝、plan/execute 分离、能力门控即不注册、契约哨兵与文档一致性测试都是真实运行的。
- **但三条核心安全主张各有一个实现缺口**：审批只绑定工具名而非参数且可重复使用（A1）；`-serve` 模式无认证并信任客户端自报的 `actor`，权限规则可被匿名改写（A2）；哈希链不覆盖事件信封字段，"审计防抵赖"打折（A3）。
- **数据层有一处连锁缺陷**：`events.tool` / `events.request_id` 两列从未写入，导致待审批视图失效、按工具计数视图失真、审计 CSV 两列恒空（A4）。
- 另有作用域对 nmap 范围写法的放行（A5）、四处与 README 描述不符的功能问题（B6–B9）、若干骨架与漂移（B10–C16）。

严重度口径：**高** = 直接违背安全内核的核心主张；**中** = 功能/审计与文档不符，或存在护栏绕过；**低** = 漂移、死代码、demo 保真度。本文所有护栏（作用域 / allowlist / denylist）按项目自身定义均为"防误用"而非安全边界，评级已考虑这一点。

## 3. 实际架构

```
cmd/pat ──▶ app（唯一装配点）──▶ core/{perm,tool,event,loop,session,agent,provider,util}
ui/cli  ──┘        └──▶ gateway/{msf,nmap}（只实现 core 声明的接口）
server ──┘
```

README §2 的目录树（`go.work`、`cmd/pat-tui`、`ui/tui`、`core/audit`、`core/bus`、`gateway/toolnmap`）是目标架构，与当前代码不对应，见 C14。

关键机制（均已读码核对）：

| 机制 | 位置 | 要点 |
|---|---|---|
| 权限四层 | `core/perm/engine.go` `Check` | 环境闸门 → 能力门控 → 作用域 + exec 策略 → 规则首条命中；默认 deny |
| exec 策略 | `core/perm/exec.go` | 剥掉 `sudo/env/timeout/proxychains4` 等包装器后对真实二进制做 case-sensitive glob；deny 优先、空 allowlist 全拒、悬空包装器 fail closed |

### A. 安全内核

#### A1 审批只绑定工具名，不绑定参数，且永不消费 —— 高

- **实现**：`core/tool/executor.go:78` 只比对 `a.Tool != name`；`Approval` 结构体虽保存了 `Args`，但 `Run` 不比对；批准后 `State` 永远停在 `approved`，没有一次性消费或过期。
- **声明**：`README.md:21`（"`requestId` 与工具一一绑定"）、`README.md:440` 与 `docs/security-model.md:18`（"审批请求与 tool call 一一绑定"）。security-model 的措辞其实已暴露实现只匹配 `Tool`。
- **实测**：同一 `requestId` 先以 `RHOSTS=192.168.56.10, ports=445` 执行成功，再以 `RHOSTS=192.168.56.20, ports=22` 执行同样成功（见附录 A 步骤 3–4）。
- **影响**：一次人工批准 = 该工具对**任意清单内目标**的无限次执行许可。作用域与 exec 策略仍在运行时生效，所以波及面限于实验清单，但"批准的是什么就执行什么"这一审批语义不成立。
- **建议**：`Run` 时比对审批记录中的 args 规范化哈希；执行成功后将审批置为 `consumed`（同一 `requestId` 不可二次执行）；增加过期时间。

#### A2 `-serve` 无认证，信任客户端自报 `actor`，规则可匿名改写 —— 高

- **实现**：
  - `server/server.go:171`、`:207`：请求体 `actor == "agent"` 即以 agent 身份执行 / 批准，服务端不校验来源。
  - `server/server.go:246`：`POST /api/v1/permissions/rules` 直接覆盖内存中的规则，无任何闸门，不写事件。
  - `server/server.go:66`：`decode` 不校验 `Content-Type`；全局无 Origin / Host 校验、无 token。
- **实测**（附录 A 步骤 2、7、8）：以 `{"decision":"approve","actor":"agent"}` 批准成功，审计记录 `approval.resolved` 的 actor 为 `agent`；以 `Content-Type: text/plain`、无任何凭据把 `console(*)` 改为 `allow` 成功；随后 `console` 工具**未经审批**直接执行到网关（mock）。
- **分析（未实测）**：任何本机进程都能完成"改规则 → 批准 → 执行"；浏览器恶意页面借 `text/plain` 表单 + DNS rebinding 理论上也能做到，这两条路径都不需要把端口暴露到公网。文档只写了"不要绑定 0.0.0.0"。
- **建议**：服务端对执行/批准强制 actor=human（或拒绝非 human 的自报值，agent 调用走内部通道）；规则写入需 `PAT_AUTHORIZED` + 显式开关，或改为只读；校验 `Content-Type: application/json`、`Origin`/`Host` 为 loopback；远程审批加签名 token + 过期（README §13 #7 已规划，建议提前）。

#### A3 哈希链只覆盖 payload —— 中

- **实现**：`core/event/store.go:94` `e.Hash = ComputeHash(e.PrevHash, e.Payload)`；`types.go` `ComputeHash` 只序列化 payload。
- **影响**：拥有库写权限者可修改 `actor`、`type`、`tool`、`session_id`、`request_id`、`created_at` 而不破坏链——例如把某条 `approval.resolved` 的 actor 从 `agent` 改为 `human`。`TestTamperDetection` 只覆盖 payload 篡改。
- **建议**：把信封字段一并纳入 canonical JSON 再哈希；补"只改 actor / type"的篡改用例。

#### A4 `events.tool` / `events.request_id` 两列从未写入 —— 中

- **实现**：`core/event/types.go:63` `NewEvent` 没有 tool / requestID 入参，所有 emit 点只把它们放进 payload；`store.go:100` INSERT 写入的是空串。
- **实测**（Python 只读查库）：45 条事件中 `request_id` 非空 0 条；3 条 `approval.requested`、1 条 `approval.resolved`，而 `v_pending_approvals` 返回 0 行（`r.request_id = e.request_id` 对所有行都是 `'' = ''`）；`v_tool_counts` 只有 `[('', 11)]`；`/audit csv` 的 `tool`、`request_id` 两列每行都为空。
- **影响**：`idx_events_request` 失效；`api/events.md` 把 `request_id`、`tool` 列为关键字段，但审计导出拿不到；"待审批视图重放"不可用。
- **建议**：`NewEvent` 增加 tool / requestID 参数（或在 `Emitter.Emit` 前填充 `Event` 字段），所有 emit 点补齐；视图、索引、CSV 列自然恢复。

#### A5 作用域放过 nmap 范围写法 —— 中

- **实现**：`core/perm/scope.go:76` 对非 IP / 非 CIDR 的 token 调 `plausibleHostname`（`:124`），只要求字符集 `[a-z0-9-.]` 且含 `.` 或 `-`；`10.0.0.1-254`、`10.0-255.0-255.1` 都满足，仅返回 `scopeWarning`。
- **实测**（附录 A 步骤 10）：两种写法批准后均到达网关（mock 回显 `target=10.0.0.1-254`）；对照 `8.8.8.8` 被 403 拒绝。
- **影响**：与"清单外 IP 字面量直接拒绝"不符；nmap 会实际扫描整个范围。预览会显示原始 `RHOSTS`，细心的审批者可以察觉，但护栏本身失效。
- **建议**：识别 IPv4 范围 / 八位组写法，展开后逐 IP 校验，或在 `isolated_lab` 下直接拒绝；不要按"未解析主机名"仅告警。

### B. 功能与文档不符

#### B6 `/plan` 对写工具并不"永远可用" —— 中

`app/commands.go:239`：`plan()` 在预览后对写工具调用 `Executor.Run` 以创建审批，而 `Run` 先过 `perm.Check` 的 env 闸门。未设 `PAT_AUTHORIZED` 时 `/plan nmap_scan RHOSTS=… ports=445` 直接 `permission denied [env]`，exit 1，**预览不可见**。与 `README.md:218`（"只读规划 / dry-run，永远可用"）矛盾。建议：审批请求的创建不走 `Run`，或在 `Run` 中把 env 闸门推迟到真正执行前。

#### B7 自然语言模式下只读工具的输出被丢弃 —— 中

`app/app.go:192`：`} else if _, err := a.Executor.Run(c, call.Name, call.Args, ""); err == nil {` 执行了但结果弃掉。实测"看看 session"只回显"计划：session_list()"和预览，看不到会话列表。建议把 `res.Output` 追加到回复。

#### B8 状态机卡在 `awaiting_approval` —— 中

`app/app.go:198` 在创建审批后尝试转 `Observing`/`Done`，但 `core/loop/loop.go:29` 规定 `AwaitingApproval` 只能去 `Executing | Cancelled | Failed`，转换失败被 `_ =` 吞掉。之后任何自然语言输入在 `app/app.go:133` 转回 `Planning` 时报 `invalid loop transition awaiting_approval -> planning`；`/clear`（`commands.go:183`）不复位 Loop。实测复现。建议：创建审批后停在 `AwaitingApproval` 是对的，但 `HandleMessage` 应允许从 `AwaitingApproval` 重新进入 `Planning`（新输入视为放弃旧计划，或提示先 `/approve`/`/run`），`/clear` 调 `Loop.Reset`。

#### B9 审计导出被截断 —— 中

`core/tool/builtins.go:225` 返回 `util.SafeText(body, maxToolOutput)`，`maxToolOutput = 4096`（`:14`）。stdout / `GET /api/v1/audit` 只能看到前 4 KiB（实测 63 行只输出 18 行，尾部标注 `[truncated 11440 runes]`）；只有带 `path` 参数写文件才是完整正文。审计导出不应走工具回显的截断阈值。建议：导出路径不受 `maxToolOutput` 限制，或只写文件并返回路径。

#### B10 产物登记未接线 —— 中

`core/event/store.go:179` `RegisterArtifact` 没有任何生产调用方，没有工具填充 `Result.Artifacts`，`artifact.registered` 不会出现，`cleanupArtifacts`（`builtins.go:270`）永远返回 `removed=0, residue=0`。README 的"证据 → 裁决闭环"目前只有 verdict 一半。另：`ExperimentID` 为空时 `cleanupArtifacts` 会删除会话内**所有**登记产物（`tag` 判断被短路），接入产物登记前需修正。

#### B11 OpenAI 适配器是骨架 —— 低

`core/provider/openai.go:77` 工具 schema 的 `properties` 为空；`app.go` 只回填 user / assistant 文本，工具结果从不作为 tool message 返回模型；`core/agent/roles.go` 的三个 `Prompt` 没有任何引用，没有 system 消息。真实模型下基本不可用；README §0 把它列为"已交付"略乐观。

#### B12 `-backend rpc|rest` 静默降级 —— 低

`config.Validate` 接受 `rpc` / `rest`，但 `gateway/msf/msf.go:221` 的 `switch` 没有对应分支，落入 `default: // auto`，行为与 auto 相同且不报错。建议显式拒绝未实现的后端，或在启动时打印明确的降级原因。

#### B13 fake provider 端口正则 —— 低

`core/provider/provider.go:57` 第三个分支 `(\d{1,3}(?:,\d{1,3}){0,20})` 会匹配任意 1–3 位数字。README §7 的示例"扫一下 192.168.56.0/24 的 445"实测输出 `ports=192`（第二个分支要求 IP 后紧跟"的"，被 `/24` 打断）。demo 保真度问题，不影响安全。

### C. 文档漂移与死代码

#### C14 README 与代码脱节 —— 低

`README.md:65` §2 目录树列出的 `go.work`、`cmd/pat-tui/`、`ui/tui/`、`core/audit/`、`core/bus/`、`gateway/toolnmap/` 均不存在（实际为 `app/`、`ui/cli/`、`core/event/` 内含 bus、`core/tool/` 内含 audit 导出、`gateway/nmap/`）。`README.md:244` §4 功能表有 10 项标 🔲，而 `:9` §0 声明已交付——README 自己说明"保留原始排期"，但读者容易被误导。`docs/architecture.md` 分层图同样写了 `core/{…,audit,bus,…}`。建议：§2 改为实际目录，§4 状态列同步，或把 §4 改为"路线图"并去掉状态列。
